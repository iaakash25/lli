## 1. Summary

The repository is a **frontend-only design prototype** generated by Lovable. It has no backend, no database access, no authentication, no payments and no data fetching of any kind. All product, collection, review and stock data is hard-coded; cart and wishlist live in `localStorage`.

The design layer (layout, typography, motion, accessibility basics) is solid and must be preserved. Everything behind it — catalogue, cart, checkout, accounts, admin, payments — is greenfield.

Three facts shape the plan more than any others:

1. **The frontend is TanStack Start (SSR), not a plain Vite SPA.** The build targets Cloudflare by default through Nitro. Hosting on Vercel is possible but must be verified (§9, C1).
2. **The local copy is not a git repository** and no GitHub remote is configured here. Branch history, recent commits and CI cannot be audited from this copy (§2).
3. **No infrastructure details are available** to this session: no `.env` files, no AWS credentials in the environment, no `psql`, `redis-cli`, `pm2`, `nginx` or `docker` installed locally. EC2, PostgreSQL and Redis are therefore *unverified*, not *absent*.

## 6. Security observations carried into the baseline

Detailed in `SECURITY_BASELINE.md` §10. Headline items:

- No security headers (CSP, HSTS, frame-ancestors, nosniff, Referrer-Policy, Permissions-Policy).
- `.gitignore` does not cover `.env*`.
- Cart/wishlist read from `localStorage` with no schema validation; totals and stock are computed in the browser.
- `q` search parameter has no length limit and uses throwing `parse()`.
- `error-capture.ts` keeps one process-global "last error" that concurrent SSR requests can overwrite, and wraps `console.error` to emit up to 8 000 characters of stack/cause chain (a future secret-leak path once a backend exists).
- CSRF middleware in `start.ts` only covers server functions.
- Google Fonts loaded from a third-party CDN (privacy and CSP implications).
- Two high-severity dependency advisories (§5).

No XSS sink was found in application code (no `dangerouslySetInnerHTML`, `innerHTML` or `eval` outside the unread generated `ui/` folder). The generated shadcn `chart.tsx` conventionally injects CSS through `dangerouslySetInnerHTML`; it is unused and should be deleted rather than reviewed.

## 9. Conflicts with the proposed architecture

| # | Conflict | Impact | Proposed resolution |
|---|---|---|---|
| C1 | Frontend is **TanStack Start SSR** with Nitro defaulting to Cloudflare; the brief assumes a React/Vite app on Vercel. | The Vercel build may need an explicit Nitro `vercel` preset; Lovable's config says it supplies Nitro and warns against adding plugins manually. | In Phase 8 verify `vite build` under the Vercel preset in a throw-away Vercel project *before* any integration work. If it cannot be done cleanly, evaluate Vercel's Node adapter vs. keeping SSR. Do not change the framework without approval. |
| C2 | Authenticated SSR would require forwarding a cookie that lives on `api.<domain>`. | The refresh cookie is scoped to the API origin and is not sent to the SSR host. | Render **public** catalogue pages server-side; fetch **authenticated** data (account, cart, orders) client-side only. |
| C3 | Vercel preview deployments use `*.vercel.app`, which is **cross-site** to `api.<domain>`. | `SameSite` cookies will not flow; auth cannot be exercised on previews. | Use staging with a real subdomain pair (`staging.<domain>` / `api-staging.<domain>`) for auth testing; allow only explicit origins in CORS. |
| C4 | Local copy is not under git; Lovable-sync history rules apply to the GitHub repo. | Cannot audit history; risk of conflicting edits between Lovable and local work. | Confirm the GitHub remote and branch strategy (§ Open decisions D1). Work on feature branches; never force-push. |
| C5 | Two lockfiles (`bun.lock`, `package-lock.json`). | Vercel/CI may resolve different dependency trees. | Choose one package manager per package (D2). |
| C6 | `zod ^3` in frontend; audit recommends ≥ 4.6.6. | Major-version bump touches TanStack `validateSearch` usage. | Use zod 4 in the backend from day one; upgrade the frontend as an isolated, tested change. |
| C7 | Lovable-managed Vite config discourages manual plugins. | Constrains CSP-nonce, headers, env handling at build time. | Apply headers in Vercel config and at the server entry (`src/server.ts`) rather than in Vite plugins. |
| C8 | Admin requirements are large and security-critical; storefront bundle must stay small. | Shipping admin code to all customers enlarges the attack surface and bundle. | Build admin as a **separate app** on `admin.<domain>` (D3). |

No existing backend, schema, or API was found, so there is nothing to duplicate or migrate yet.

## 11. Recommended implementation sequence

See `IMPLEMENTATION_ROADMAP.md`. In short: confirm infrastructure facts → hygiene (git, lockfile, formatting, `.gitignore`) → database foundation → backend foundation and security → catalogue/admin → shopping → payments/shipping/orders → customer features → AI → frontend integration → hardening → staging.

Frontend hygiene (formatting, `.gitignore`, secrets patterns) is deliberately Phase 0.5 so that every later change is reviewable and CI can be green.
